Duas redes de dados: 20 pontos reais de Aracaju com 30 vias simuladas, e o campus da UNIT a pé (13 pontos, 21 caminhos). A rede não representa trânsito real.

Fluxo básico do usuário. Os passos 5 e 6 estão em laranja porque o desbloqueio (encerramento de incidente) é a novidade principal desta semana. Reforçar que a rede é simulada: coordenadas reais só para desenhar o mapa.

Todo o back-end é um único artefato Spring Boot: importação, cálculo de rotas e incidentes rodam no mesmo processo e compartilham o mesmo banco. A separação é lógica, por pacotes (camadas), não física. O cliente desktop é um módulo Maven à parte, mas é só um consumidor da API. Regra de camadas: controller valida e delega, service tem regras e transações, repository só persiste, DTOs separam o contrato externo das entidades.

Por que monólito

Para um domínio pequeno, um só deploy é mais simples e mais seguro

Transação única

Incidente e versão da rede mudam juntos

Bloquear uma via e subir a versaoRede acontecem na mesma @Transactional, sem coordenar serviços.

Um deploy

Sobe com um comando

mvnw -pl api spring-boot:run; o PostgreSQL vem do docker compose. Nada de rede entre serviços.

Contrato claro

A fronteira é a API REST

openapi.yaml e DTOs isolam o desktop das entidades. Se um dia separar, o contrato já existe.

O custo que aceitamos

Tudo escala junto e uma falha derruba a API inteira. Com 5 endpoints e uma equipe só, isso pesa menos que a complexidade de vários serviços.

Justificar a escolha: o domínio cabe em poucos agregados (rede, rota, incidente) que mudam juntos. Microsserviços exigiriam consistência entre bancos, descoberta de serviço e mais deploys. Mencionar o trade-off com honestidade.

Pacote raiz com.logistica.roteirizacao, projeto Maven multimódulo (api e desktop). As dependências apontam para dentro: controller depende de service, service de model e repository. O model não conhece Spring Web nem HTTP.

Uma requisição atravessando as camadas

POST /rotas, da Rodoviária (P05) até a UNIT (P01)

controller

RotaController

valida o RotaRequest (origem, destino, critério)

service

RotaService

confere se os pontos existem e monta o Grafo sem as vias bloqueadas

model

CalculadorRota

Dijkstra com o CriterioRota escolhido (polimorfismo)

repository

RotaCalculada

grava a tentativa, com ou sem caminho, e a versão da rede

dto

201 RotaResponse

P05, P15, P01 · 8,5 km · 14,5 min

Erro em qualquer camada → TratadorErrosApi → { status, erro, campo, mensagem }

Tudo isso acontece num único processo e numa única transação (@Transactional no RotaService). Sem caminho não é erro: a resposta é 201 com status SEM_CAMINHO e a mensagem explicando as vias bloqueadas. Origem inexistente gera 404 com o campo apontado.

Na API: o incidente fica no histórico com ativo = false e encerradoEm, e a versaoRede sobe. Já encerrado dá 409; id inexistente dá 404.

Na tela: o painel 4 ganhou o combo Bloqueada e o botão Desbloquear via (Alt+U). Cada via aparece só na lista em que faz sentido.

Antes, um incidente era para sempre. Agora o ciclo fecha: bloquear, recalcular, desbloquear, recalcular. Exemplo real da rede de Aracaju: Rodoviária até UNIT. Testado em IncidenteControllerTest (API) e JanelaPrincipalTest (desktop). Se a API responder 409 ou 404, a tela libera a via mesmo assim e avisa.

Demonstração ao vivo

Roteiro de 3 minutos

  1. Subir a API (perfil dev já carrega a rede de Aracaju) e abrir o desktop.
  2. Importar a rede e clicar no mapa: Rodoviária (P05), depois UNIT (P01).
  3. Conferir 8,5 km e 14,5 min, passando por P15.
  4. Bloquear V24: rota recalculada para 11,7 km, via tracejada no mapa.
  5. Desbloquear V24: a rota volta a 8,5 km.
  6. Exportar a rota em CSV e reabrir a janela para mostrar o config.bin.

mvnw -pl api spring-boot:run · mvnw -pl desktop compile exec:java

No Windows usar mvnw.cmd. Rodar o desktop da raiz do repositório para achar dados/tratados. Se a porta 8080 estiver ocupada, subir em 8081 e passar a URL ao desktop (ver README). Plano B: ter um vídeo ou capturas de tela do fluxo.
